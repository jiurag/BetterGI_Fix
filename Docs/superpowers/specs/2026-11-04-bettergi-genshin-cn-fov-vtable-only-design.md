# BetterGI 国服原神 FOV vtable-only 性能优化设计

## 1. 背景

当前 FOV 功能可正常工作，但开启后跑图只能维持约 `105 FPS`，
关闭 FOV 时约为 `122 FPS`。本机运行态已确认：

1. CameraPose 探针每秒执行约 `122` 次，和当前约 `120 FPS` 基本一一对应。
2. 探针每次扫描相机对象约 `0x4000` 字节，并执行大量原子计数和诊断写回。
3. `SetField` 最近 2 秒产生约 `8563` 次单步异常，累计已约 `94 万` 次。
4. CameraPose 已成功切到 vtable 第 `6` 槽，硬件断点已经撤除。
5. `SetField` 和 `Synchronize` 仍长期使用硬件断点，是剩余异常开销来源。
6. 测试版 `0.66.4-alpha.1` 运行态进一步确认：`SetField` 和 `Synchronize`
   在相机 vtable 中均找不到精确匹配槽位，错误码为 `1168`；强制 FOV 期间
   两个辅助入口持续产生每秒约 `3500` 至 `3800` 次 FOV 调用或调试异常。

本设计选择方案 B：三个 FOV 入口都优先尝试相机类堆内 vtable 接管，
但强制模式以 CameraPose vtable 作为最终视角热路径。CameraPose 接管后，
`SetField`、`Synchronize` 不再长期保留硬件断点；只有 CameraPose 尚未接管或
接管丢失时，才允许辅助入口短暂降级。

## 2. 目标

1. FOV 开启并跑图时，实测帧率应恢复并稳定在目标值附近。
2. `SetField`、`Synchronize`、`CameraPose` 三个入口都优先尝试 vtable 接管；
   强制 FOV 的最终渲染路径以 CameraPose vtable 为准，辅助入口无法匹配时不得
   长期驻留高开销硬件断点。
3. CameraPose 探针不再进入正式热路径，不再每帧扫描 `0x4000` 字节。
4. 不修改游戏模块代码页、不修改 `.rdata`、不修改磁盘游戏文件。
5. vtable 接管失败时不得静默失去 FOV；允许明确降级回现有硬件断点。
6. 保持强制 FOV 模式、目标滑条、持久化和现有停止恢复顺序。
7. 保留安装失败、命中、替换、槽位和回退状态的可观测性。

## 3. 非目标

1. 不修改去雾和帧率解锁实现。
2. 不恢复会修改游戏代码页的旧内联 Hook。
3. 不修改游戏 `.rdata` 分派表；该路径此前实测会导致游戏自行退出。
4. 不实现反作弊隐藏、检测绕过或账号安全承诺。
5. 不承诺游戏更新后 vtable 布局保持不变。
6. 不在本优化中改变 FOV 数值范围、UI 控件或配置格式。

## 4. 已核验依据

1. 当前 CameraPose vtable 接管代码位于
   `GenshinFpsUnlockHook.cpp`，只接受与特征码目标完全一致的唯一槽位。
2. 当前 vtable 写入只修改实例所属 Il2CppClass 的堆内 vtable 项。
3. 当前 CameraPose vtable 已处于 Active，且 `HardwareHookRemoved=1`。
4. 当前 FOV 无安装错误，目标为 `60`，说明堆内 vtable 接管路线可运行。
5. `SetField` 和 `Synchronize` 已由唯一特征码定位到真实游戏函数。
6. `SetField` 和 `Synchronize` 是否同时存在于当前相机类 vtable，属于
   `未知/未验证`；必须在运行期按精确函数地址唯一匹配后才能接管。
7. 当前探针映射和 FOV 共享状态已有读取工具和契约测试，不能在未同步修改
   测试的情况下删除或重排字段。

## 5. 采用方案

### 5.1 总体流程

1. 仍由特征码定位 `SetField`、`Synchronize`、`CameraPose` 三个真实函数。
2. 首轮只在 `CameraPose` 上安装临时硬件断点，用于取得相机实例。
3. 首次 CameraPose 命中时，从实例读取 Il2CppClass 和 vtable。
4. 在同一 vtable 中分别查找三个真实函数的唯一匹配槽位。
5. 对匹配成功的入口写入 detour；零匹配或非唯一匹配的入口记录诊断，
   不再假定它一定存在于相机 vtable。
6. 确认 CameraPose vtable detour 已命中后，撤除临时 CameraPose 硬件断点。
7. 强制模式下，CameraPose 是最终渲染位姿的唯一权威热路径；确认它已接管后，
   停用 `SetField`、`Synchronize` 的辅助硬件断点，并禁止工作线程重新安装。
8. 如果 CameraPose vtable 尚未生效或接管丢失，辅助入口可恢复硬件断点作为
   启动期安全降级；CameraPose 重新接管后再次停用。
9. 后续每轮只检查仍由 vtable 接管的槽位是否被游戏恢复；需要时重新写入。
10. FOV 关闭或会话停止时，按 `CameraPose`、`Synchronize`、`SetField` 的顺序
   恢复仍由本工具占用的 vtable 项。

### 5.2 热路径

1. `HookUpdateCameraPose` 不再调用 `CaptureFovCameraProbe`。
2. 首次 vtable 接管前只记录一次轻量相机实例指针。
3. vtable 接管完成后不再每帧写实例、线程、指针或候选字段。
4. 已接管的 detour 只保留 FOV 替换所需的原子读取和命中计数。
5. 逐帧候选项扫描、类结构解析和 `0x4000` 字节统计仅保留在显式调试开关中。

### 5.3 vtable 接管

1. 三个入口复用同一套“目标函数、detour、槽位、原始函数、状态、命中数”模型。
2. 槽位必须同时满足：
   1. 槽位数在有效范围内。
   2. 当前槽值精确等于特征码定位到的真实函数。
   3. 同一目标在 vtable 中只出现一次。
3. 不按固定槽号硬编码 `SetField` 或 `Synchronize`。
4. 写入前只把目标 vtable 项临时设为可写，写入后立即恢复原保护属性。
5. 写入失败、槽值被第三方改写或槽位不再唯一时，不覆盖未知地址。

### 5.4 安全降级

1. CameraPose vtable 成功接管时，强制 FOV 状态为 Ready；`SetField` 和
   `Synchronize` 的 vtable 失败不再被视为强制 FOV 失败。
2. 强制模式确认 CameraPose vtable 接管后，辅助入口的硬件断点必须停止；
   否则视为性能修复未完成。
3. 普通 FOV 模式继续使用 `SetField` 路径，不改变现有行为。
4. 如果 CameraPose vtable 不可用，辅助入口硬件断点可临时保留，保证功能
   安全降级；但必须通过诊断标记明确显示性能仍未恢复。
5. 降级必须写入诊断状态和日志，不能伪装成完整性能路径。

## 6. 运行状态和日志

1. 保留现有共享内存布局和字段顺序。
2. 复用三个 Hook 的命中、替换和错误诊断块。
3. 新增启动日志：
   1. 三个目标函数 RVA。
   2. 三个 vtable 槽号。
   3. 每个入口是 vtable 还是硬件断点降级。
4. 首次 vtable 命中时，每个入口只记录一次。
5. 槽位被游戏恢复后重新写入时只累计次数，不持续刷日志。
6. 任一入口从 vtable 降级或恢复失败时记录一次明确错误。

## 7. 停止与恢复

1. 正常停止继续先停止 FOV，再停止去雾和帧率。
2. FOV 内部先停止新的替换请求，再恢复三个 vtable 项。
3. 如果槽值已经不是本工具 detour，不覆盖当前值。
4. 任一 vtable 恢复失败不得跳过去雾和帧率恢复。
5. 临时 CameraPose 硬件断点若仍存在，必须在 vtable 路径或降级路径确定后移除。

## 8. 测试与验收

### 8.1 自动化

1. 更新 FOV 契约测试，禁止 `HookUpdateCameraPose` 热路径调用重量探针。
2. 验证三个目标都通过“精确地址、唯一槽位”规则匹配。
3. 验证 vtable 写入前后保护属性恢复。
4. 验证游戏恢复槽位后只重写已知原函数。
5. 验证停止时不会覆盖未知 vtable 值。
6. 验证硬件断点降级状态可被日志和诊断读取。
7. 运行现有 FOV、去雾、帧率和共享状态测试。

### 8.2 黑盒

1. 同一场景、同一路线先关闭 FOV 记录 60 秒基线。
2. 开启 FOV 和目标 `60`，沿同一路线再记录 60 秒。
3. 从游戏 `LocalLog.log` 的 fractional timestamp 和 `FrameCount` 计算实际 FPS。
4. 验收目标：FOV 开启后中位帧率接近关闭 FOV 的基线，不长期停在约 `105 FPS`。
5. 确认 CameraPose vtable 持续命中；SetField 和 Synchronize 的辅助硬件
   断点已撤除且不再增长。辅助入口若因当前客户端不存在 vtable 槽位而失败，
   应显示为明确的“已降级但已停用”，不能继续产生每秒数千次异常。
6. 确认 `FovStatus=Ready`、目标正确、无 `FovInstallError`。
7. 连续验证转动视角、角色技能、大型物体碰撞、空中快速移动和剧情镜头。
8. FOV 画面不得出现闪回；若发生闪回，本方案判定失败。
9. 固定场景停留观察 `10010`、`10010-4001`、资源完整性错误和 Hook 失败。
10. 关闭 FOV 后确认恢复原视角，去雾和帧率继续工作。

## 9. 风险

1. `SetField` 和 `Synchronize` 已在当前客户端确认不存在于相机类 vtable；
   强制模式因此只把它们用于 CameraPose 接管前的短暂降级，最终性能依赖
   CameraPose vtable 是否持续有效。
2. 游戏可能绕过 vtable 直接调用真实函数；降级判定必须通过实际命中覆盖。
3. 游戏更新可能改变 Il2CppClass vtable 偏移、槽位数量或函数布局。
4. vtable 槽位可能在运行中由游戏重写；每轮校验会增加少量工作线程开销，
   但不进入渲染线程热路径。
5. 辅助硬件断点撤除后，如果某个镜头流程绕过 CameraPose 最终位姿写入，
   可能出现新的 FOV 闪回；必须完成技能、碰撞、剧情和快速移动黑盒验收。
6. 游戏更新可能让 CameraPose vtable 暂时失效；此时必须恢复辅助硬件断点
   保证功能，但性能验收会失败，不能宣称完整修复。

## 10. 发布门槛

1. 自动化测试全部通过。
2. 黑盒帧率实测达到验收目标。
3. 技能、碰撞、快速移动和剧情均无 FOV 闪回。
4. 无 `FovInstallError`、无重复安装失败日志。
5. 固定场景观察未出现新增 `10010` 或资源完整性误报。
6. 未完成以上项目前，不打正式标签、不覆盖当前正式版发布。
